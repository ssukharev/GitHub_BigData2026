# Сбор истории звёзд

Сборщик `stars.py` читает `GET /repos/{owner}/{repo}/stargazers/history` и записывает дневные значения в `core.star_history_daily`. Нужны Python 3.9+, PostgreSQL с миграциями V1–V3 и заполненная `core.repos`.

Из корня репозитория:

```bash
python3 -m venv /tmp/gh-stars-venv
/tmp/gh-stars-venv/bin/python -m pip install -r analytics-py/collectors/requirements-stars.txt
/tmp/gh-stars-venv/bin/python analytics-py/collectors/stars.py --limit 5
```

В `.env`: `GITHUB_TOKEN`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`; необязательные `POSTGRES_HOST`, `POSTGRES_PORT`. Вместо `POSTGRES_*` можно задать `DATABASE_URL`. Секреты в репозиторий не добавляются.

```bash
python analytics-py/collectors/stars.py --repo psf/requests
python analytics-py/collectors/stars.py --refresh
python analytics-py/collectors/stars.py --refresh --resume
```

Без `--refresh` уже записанные репозитории пропускаются. `--refresh` обновляет их значения через upsert: удалённые звёзды могут менять прошлые значения. До записи проверяется весь ответ, включая достижение недели создания репозитория (`core.repos.created_at`); ошибка HTTP, обрезанный снимок, нарушенная последовательность недель или неверные `days` оставляют прежние данные репозитория без изменений. Нули берутся только из явно опубликованных `days`; неизвестные недели не заполняются нулями.

Самый новый API-бакет недели консервативно исключается даже тогда, когда он кажется полным по UTC-календарю. Завершение остальных недель подтверждается началом следующей, более новой недели API. Это может оставить последний полный бакет за пределами результата, зато текущая неполная неделя не становится целевой переменной модели.

## Метки дней и ограничения времени

GitHub [не гарантирует совпадение границ дней и недель с UTC](https://docs.github.com/en/rest/activity/starring?apiVersion=2026-03-10#get-repository-star-history). `days[0]` относится к воскресенью календаря источника, но часовой пояс границ API не указан.

`day` в этой таблице — **метка API-бакета**, вычисленная как UTC-дата исходного `week` плюс индекс `days[]`. Это соглашение о метках, а не утверждение, что звёзды поставлены между 00:00 и 24:00 UTC указанного дня. Сборщик не переносит даты к ближайшему воскресенью и не подбирает неизвестное смещение.

По этим агрегатам нельзя восстановить точные UTC-сутки. Поэтому `day` нельзя без оговорки объединять с UTC-днями/неделями коммитов или использовать для вывода о местном часе активности. Для точного выравнивания нужна дополнительная информация о границах источника. В частности, группировка этих меток в `W-SAT` не доказывает совпадение со статистикой коммитов.

Проверка целостности консервативна: соседние начала недель должны отличаться на 6–8 суток; это допускает сдвиг календарной границы/DST, но выявляет пропущенную неделю. Дубли, пересекающиеся метки дней и интервалы вне этого диапазона останавливают запись репозитория для проверки. Промежуток в метках после сдвига границы остаётся промежутком — искусственных нулей нет.

## Ошибки и продолжение

`core.checkpoints` хранит позицию и отдельную очередь `failed_repo_ids`. Они обновляются одной транзакцией. `--resume` выбирает как новые id после позиции, так и ранее неудачные id, поэтому ошибка на раннем репозитории не теряется после успехов на следующих.

Обычный запуск, `--refresh` и `--repo owner/name` имеют отдельные ключи чекпоинтов. Новый запуск без `--resume` начинает выбранный режим заново. После обновления со старой версии первый `--refresh` следует запустить без `--resume`: прежняя версия не сохраняла очередь ошибок.

После временных сетевых ошибок и 5xx запросы повторяются. Primary/secondary rate limits учитывают `Retry-After` и время сброса квоты. Ошибка токена, исчерпанные попытки лимита или соединения останавливают запуск; 404/неверный ответ отдельного репозитория остаются в очереди повторных попыток. Любая неустранённая ошибка даёт `collection_runs.status = failed`, список id в `stats` и ненулевой код завершения. Неудачные репозитории с 404 требуют проверки: сборщик не объявляет их успешно собранными.

## Проверка без GitHub и секретов

```bash
python -m pip install -r analytics-py/collectors/requirements-stars-test.txt
python -m pytest analytics-py/tests/test_stars.py
```

Тесты используют подставные HTTP-ответы и подменённые операции БД. Импорт модуля не читает `.env`; в тестах загрузка конфигурации отключена. Они проверяют страницы, границы и целостность бакетов, ограничение частоты, повтор ошибок после прерывания и журнал запуска.

Четыре дополнительные проверки PostgreSQL включаются переменной `STARS_TEST_DATABASE_URL`. Она должна указывать на отдельную временную БД с именем `stars_review_*` и миграциями V1–V3. Проверяются SQL-выборка очереди ошибок, атомарность позиции/очереди, upsert с откатом при ошибке и журнал запуска. Тесты создают только искусственные записи и удаляют их после проверки; БД проекта использовать для этого не следует.
