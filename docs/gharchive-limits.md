# GH Archive: источник, ограничения и матрица валидности ряда

Документ для всех, кто читает `core.gh_activity_hourly` и `core.gh_activity_monthly` (Антон, задача 2; Сергей, задача 1) и пишет про них в статье. Все числа ниже получены 16.11.2026 из загруженных таблиц и прямыми запросами к ClickHouse, если не сказано иное. Время везде UTC.

## Откуда данные

GH Archive (gharchive.org) записывает публичную ленту событий GitHub, один файл JSON на час. Мы не качаем файлы, а берём готовые агрегаты из публичной копии архива в ClickHouse: таблица `github_events` на `play.clickhouse.com`, пользователь `play`, доступ по HTTP без регистрации. BigQuery (`githubarchive.*`) нужен только для необязательной сверки одного месяца.

Устройство таблицы определяет стоимость запросов: ключ сортировки `(event_type, repo_name, created_at)`, партиций нет. Фильтр по `event_type` отсекает чтение, а фильтр по дате почти нет. Поэтому один день стоит почти как год (все типы за 2024-03-06: 7,54 млрд строк по `EXPLAIN ESTIMATE`), а запросы делятся на `PushEvent` и остальные типы без потерь.

Сборщик: `java -jar collector/app/target/collector.jar --source=gharchive --from=2018-01-01 --to=2026-07-31 [--resume]`, код в `collector/gharchive`, SQL в `collector/gharchive/src/main/resources/clickhouse/`.

## Что лежит в таблицах

| Таблица | Ключ | Строк (2018-01..2026-07) | Что внутри |
|---|---|---|---|
| `core.gh_activity_hourly` | `(ts_hour, event_type, is_bot)` | 1 878 093 | события по часам, типам и признаку бота |
| `core.gh_activity_monthly` | `(month, event_type, is_bot)` | 2 906 | то же по месяцам, плюс `repos` и строки `CreateEvent:repository` |

Определения полей (одинаковые в обеих таблицах, записаны и в SQL):

| Поле | Как считается | Что помнить |
|---|---|---|
| `is_bot` | `endsWith(actor_login, '[bot]')` | ловит только GitHub Apps. Боты и ИИ-агенты под обычными аккаунтами считаются людьми. Отдельного класса "тяжёлых" аккаунтов (без `[bot]`, но с сотнями тысяч пушей) нет: это оговорка для статьи |
| `actors` | `uniq(actor_login)` | **приблизительно** (отклонение от точного счёта доли процента). По часам не суммируется: один человек активен во многих часах. Месячное значение считается отдельным запросом |
| `repos` (только месяцы) | `uniq(repo_name)` | приблизительно; по имени, а не по id: переименованный репозиторий считается дважды |
| `commits` | `sum(least(push_distinct_size, 100))` по `PushEvent` | у остальных типов `NULL`. С 2025-10-01 `NULL`, а не 0: GitHub убрал размер push из событий. Отсечка 100 - предложение, см. вопрос к команде ниже |
| `CreateEvent:repository` | `CreateEvent` с `ref_type = 'repository'` | новые репозитории, только в `monthly`, только 2018-01..2025-04. Это **подмножество** `CreateEvent`: складывать их нельзя |

В копии нет `actor.id`, `repo.id`, организаций и сырого `payload`, поэтому люди и репозитории считаются по логину и имени.

Типы событий, которые есть не весь период: `PullRequestReviewEvent` появляется с 2020-08, `DiscussionEvent` с 2025-09. `WatchEvent` (это звезда, а не подписка) никогда не бывает у `[bot]`, поэтому у него одна строка на месяц.

## Лимиты и квота playground

Проверено запросами к `system.settings` и `system.quota_usage` 16.11.2026, версия сервера 26.10.3.7, часовой пояс сервера `Etc/UTC`.

| Лимит | Значение | Что будет при превышении |
|---|---|---|
| время запроса `max_execution_time` | 60 с | код 159, HTTP 408 |
| строк на чтение за запрос `max_rows_to_read` | 20 млрд | код 158 |
| строк в результате `max_result_rows` | 1 000 000 | ошибка, сузить запрос |
| память запроса `max_memory_usage` | 20 ГБ | код 241 |
| `readonly` | 1 | `SETTINGS ...` в запросе: код 164 |
| квота на IP, окно 3600 с: прочитанных строк | **300 млрд** | код 201 |
| та же квота: запросов | 3000 | код 201 |
| та же квота: строк в результатах | 300 млн | код 201 |

Квота считается **на IP-адрес** и окно фиксированное (начинается с первого запроса). Все, кто сидит за одним адресом (университет, VPN, одна квартира), делят 300 млрд строк в час. Перед полной загрузкой договоритесь в чате.

Как клиент реагирует на ошибки: код 201 - ждёт до конца окна (время в тексте ошибки, `Interval will end at ...`) плюс 5 секунд, не больше двух раз на запрос; коды 202, 209, 210 и ответы прокси 429, 502, 503, 504 без кода - повтор с паузой; всё остальное, в том числе ошибка SQL со статусом 500 и таймаут 159, - сразу ошибка запуска, потому что повтор только сожжёт квоту. Параметр `wait_end_of_query=1` (пользователю `play` его менять можно) заставляет сервер дописать ответ до заголовков: тогда `X-ClickHouse-Summary` содержит все прочитанные строки, а ошибка приходит со своим статусом.

## Что изменилось в 2025-2026 годах: ряд не однороден

**Ступенька 23.05.2025 около 16:00 UTC.** Объём **всех** типов падает одной ступенькой. По часам 23.05: 15:00 - 262 958 событий, 16:00 - 213 245, 17:00 - 155 678. Отношение суточного итога к медиане того же дня недели за 2024 год: 1,08-1,10 в будни до ступеньки, 1,02 в пятницу 23 мая, 0,85 в субботу, 0,66-0,74 в будни после. Доля `PushEvent` почти не меняется, поэтому по доле ступеньку не видно. Май 2025 - частичный месяц.

**Payload урезан (объявлено в changelog GitHub от 08.08.2025).** Последний нормальный час - 2025-10-08 16:00. С 17:00 `push_size` и `push_distinct_size` равны 0 у всех `PushEvent`, а у всех `CreateEvent` `ref_type = 'branch'`. Поэтому `commits` в наших таблицах `NULL` с 2025-10-01 (весь октябрь, полмесяца не храним), а `CreateEvent:repository` загружается только до 2025-04. Контроль: `commits` за 2025-09 - 99 458 882, за 2025-10 - `NULL`.

**Дыра 2025-10-08 17:00 .. 2025-10-14 20:00.** Часы есть, но почти пустые. В 16:00 8 октября 163 656 событий, в 17:00 - 986, в 12:00 11 октября - 600, в 20:00 14 октября - 895, в 21:00 - снова 118 572. Проверка "в сутках 24 часа" эту дыру не видит: для неё нужна проверка часов с `events` намного ниже медианы того же часа недели.

**Деградация 2026.** Не-push типы выдыхаются: `WatchEvent` за месяц 2,96 млн (январь), 2,22 млн (февраль), 1,79 млн (апрель), 0,31 млн (июнь), 0,08 млн (июль) против ~6-7 млн в 2024-2025. Доля `PushEvent` растёт: 67% (февраль), 85% (июнь), 92% (июль). Доля `[bot]` среди push: 27,6% в марте 2025, 21,8% в феврале 2026, 10,3% в июле 2026.

**С августа 2026** копия теряет события (в том числе дни с нулём `PushEvent`), поэтому сборщик не загружает дальше `collector.gharchive.to = 2026-07-31`. Загрузить дальше можно только сознательно: `--collector.gharchive.to=2026-10-31`.

| 2 | 2025-05-24 .. 2026-01 | только доли и отношения (доля ботов, доля типа) с оговоркой про ступеньку 23.05.2025 16:00 UTC; абсолютные числа с периодом 1 несопоставимы; 2025-10-08 17:00 .. 2025-10-14 20:00 - дыра |

## Для задачи 2 (Антон): сезонность

- Все часы в UTC, это время события (push), а не время коммита. Часовых поясов и стран нет; переход на летнее время сдвигает "местный" суточный цикл на час дважды в год.
- Пропущенный час - это `NaN`, а не 0: перед разложением ряда строить полную сетку (75 216 часов за 2018-01..2026-07) и решать, как заполнять 485 пропусков.
- `actors` по часам не складывать в сутки и месяцы: для месяцев есть отдельное значение в `gh_activity_monthly`.
- Для длинного ряда брать период 1 (до 2025-04 включительно). Ступенька 23.05.2025 и деградация 2026 - артефакты источника, а не поведение людей.
- `is_bot` отделяет только GitHub Apps; автоматизация под обычными аккаунтами остаётся в "людях".
- Скачки `IssuesEvent` (10-11.2024) и рост `PushEvent` (10-12.2023) - не сезонность.

## Что GH Archive не даёт в принципе

- `actor.id`, `repo.id`, организации, id события и сырой `payload` (в копии ClickHouse их нет), список и сообщения коммитов;
- приватную активность и снятие звёзд (`WatchEvent` только "started");
- метаданные репозитория (язык, лицензия, размер): они в `core.repos`;
- полноту: лента - выборка событий Events API с непостоянной долей захвата, а не все действия на GitHub.

## Вопрос к команде: отсечка `commits` на 100

Это предложение, а не решение. Один пуш может нести огромное число коммитов (зеркала, импорт истории); без отсечки большая часть "коммитов" - мега-пуши, и ряд измеряет импорты. По проверке автора учебника на марте 2024: 0,12% пушей несут больше 100 коммитов, сумма `push_distinct_size` без отсечки 363 млн, с отсечкой 100 - 131 млн, 1000 - 173 млн. Минус отсечки: реальные большие пуши недосчитываются, и результат зависит от порога. Варианты: 100 (сейчас), 1000, или хранить оба значения. Если решим иначе, меняются `hourly_activity.sql`, `monthly_activity.sql` и этот документ, затем полный перезапуск сборщика.

## Комментарии к колонкам (предложение миграции)

Определения выше стоит записать в саму БД. Миграция не добавлена, чтобы не занимать номер версии параллельно с другими ветками; текст готов для следующего свободного номера:

```sql
COMMENT ON COLUMN core.gh_activity_hourly.is_bot  IS 'endsWith(actor_login, ''[bot]''): GitHub Apps; боты и ИИ-агенты под обычными аккаунтами считаются людьми';
COMMENT ON COLUMN core.gh_activity_hourly.actors  IS 'uniq(actor_login), приблизительно; по часам не суммируется';
COMMENT ON COLUMN core.gh_activity_hourly.commits IS 'PushEvent: sum(least(push_distinct_size, 100)); NULL у остальных типов и с 2025-10-01 (размер push убран из источника)';
COMMENT ON COLUMN core.gh_activity_monthly.actors  IS 'uniq(actor_login) за месяц отдельным запросом, не сумма по часам';
COMMENT ON COLUMN core.gh_activity_monthly.repos   IS 'uniq(repo_name): по имени, переименованный репозиторий считается дважды';
COMMENT ON COLUMN core.gh_activity_monthly.commits IS 'То же определение, что в gh_activity_hourly; NULL с 2025-10';
```

## Как проверить загрузку

```sql
SET TIME ZONE 'UTC';
-- пропущенные часы (ожидается 65, 6, 485)
WITH grid AS (SELECT d::date AS day FROM generate_series('2018-01-01'::date, '2026-07-31'::date, interval '1 day') d),
     have AS (SELECT (ts_hour AT TIME ZONE 'UTC')::date AS day, count(DISTINCT ts_hour) AS hours
              FROM core.gh_activity_hourly GROUP BY 1)
SELECT count(*) FILTER (WHERE coalesce(h.hours, 0) < 24) AS bad_days,
       count(*) FILTER (WHERE h.hours IS NULL)           AS absent_days,
       sum(24 - coalesce(h.hours, 0))                    AS missing_hours
FROM grid g LEFT JOIN have h USING (day);
-- последний запуск
SELECT id, status, rows, params, stats FROM core.collection_runs WHERE source = 'gharchive' ORDER BY id DESC LIMIT 1;
```

Контрольный день 2024-03-06: 24 часа, 628 строк, 5 899 775 событий, из них `PushEvent` 3 620 497 (люди 2 994 675, боты 625 822). Январь 2018 в `monthly`: 26 строк; `PushEvent`, люди: `events = 21079804`, `actors = 1280514`, `repos = 2363779`, `commits = 31109199`.
