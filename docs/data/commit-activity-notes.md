# Активность коммитов github-commits: источник, ограничения, пилот

Текст для раздела статьи "Данные". Код: `CommitActivityCollector`, `CommitActivityRepository`,
`RepoRepository.findRefs` и `RepoRepository.updateContributorStats` в `collector/github`.

## Что собирается

- **Источник**: REST `GET /repos/{owner}/{repo}/stats/contributors`. Ответ - массив авторов, у каждого
  массив недель за всю историю ветки по умолчанию: `w` (начало недели, Unix-время), `c` (коммиты),
  `a` и `d` (строки, нам не нужны).
- **Какие репозитории**: все строки `core.repos` с `created_at` в `[--from, --to]` (дни UTC) и
  `stars >= --min-stars`, по `id`. Выборку делает `github-repos`, этот сборщик её не меняет:
  `--limit=N` берёт первые N по `id` и нужен только для пробных прогонов. В базе 5492 репозитория,
  все созданы 2018-01-01..2025-12-31 и имеют `stars >= 10`.
- **`core.repo_commits_weekly`** `(repo_id, week, commits, contributors)`:
  - `week` - дата из `w` по UTC, это воскресенье;
  - `commits` - сумма `c` по авторам ответа;
  - `contributors` - число авторов с `c > 0` в эту неделю.
- **`core.repos.stats_truncated`** - в ответе ровно 100 авторов или 490 и больше, он, скорее всего,
  обрезан (ниже).
- **`core.repos.contributors_total`** - все контрибьюторы, включая анонимных: номер последней
  страницы `GET /repos/{owner}/{repo}/contributors?per_page=1&anon=1` из заголовка `Link`
  (`rel="last"`), без `Link` - длина тела (0 или 1).
- Тело ответа `/stats/contributors` в `raw.github_responses` и в лог не попадает: оно разбирается
  один раз и забывается (у pallets/flask 3,1 МБ).

## Неделя

- Метка недели - воскресенье 00:00 UTC, как её отдаёт GitHub. Проверка на данных:
  `SELECT DISTINCT extract(isodow FROM week) FROM core.repo_commits_weekly` даёт одно значение, 7.
- В pandas те же границы даёт частота `W-SAT` (неделя кончается субботой). `resample("W-SAT")`
  подписывает неделю субботой, поэтому метку берите так:

```python
weeks = pd.read_sql("SELECT repo_id, week, commits, contributors FROM core.repo_commits_weekly",
                    engine, parse_dates=["week"])
stars["week"] = stars["date"].dt.to_period("W-SAT").dt.start_time   # star_history_daily в те же недели
```

- **Последняя неделя ряда неполная**: ряд идёт до недели сбора (сбор 19.11.2026 - последняя метка
  2026-11-15). Её надо отбрасывать или помечать.
- Ряд тянется до недели сбора и у заброшенных репозиториев: нули в конце - это "коммитов не было".

## Ноль, NULL и отсутствие строки

| Что в данных | Значит |
|---|---|
| строка с `commits = 0` | в эту неделю коммитов не было (измерено); в полном сборе 90,4% строк нулевые |
| у репозитория нет строк | статистики нет: чекпоинт `empty` или `missing`, или не дождались (ниже) |
| `contributors IS NULL` | неизвестно; основной источник всегда пишет число, `NULL` оставлен для запасного источника без авторов |
| `contributors_total = 0` | в репозитории нет коммитов (список контрибьюторов пуст) |
| `contributors_total IS NULL` | неизвестно: 403 у гигантских репозиториев или 404 |
| `stats_truncated IS NULL` | репозиторий не обработан этим сборщиком |

Ответ 200 или 204 - вся история ветки по умолчанию на момент запроса, поэтому он заменяет недели
репозитория целиком (`CommitActivityRepository.replaceWeeks`, ревью #52): недели, которых в ответе
больше нет, удаляются, остальные обновляются, `[]` и 204 очищают репозиторий. Это один SQL-оператор:
если какая-то строка не прошла проверку, удаление откатывается вместе со вставкой и старый снимок
остаётся целым. Ответ сначала проверяется целиком (у каждой недели целые `w` и `c >= 0`); 202, 404,
ошибки и испорченный ответ старые недели не трогают. Для оставшихся недель `contributors =
COALESCE(EXCLUDED.contributors, w.contributors)`: известное число не затирается `NULL`.
`contributors_total` обновляется так же, `stats_truncated` - всегда свежим значением. Запасной
источник с частью истории (последние 52 недели `/stats/commit_activity`) должен писать через
`upsertWeeks`, который ничего не удаляет.

## Ограничения источника

1. **Только ветка по умолчанию.** Документация REST: статистика кешируется по SHA этой ветки;
   документация графика Contributors: коммиты других веток не учитываются.
2. **Без merge-коммитов** (и без пустых коммитов у статистики по авторам).
3. **Только авторы, привязанные к аккаунту GitHub.** Коммиты с адреса, который не принадлежит ни
   одному аккаунту, в статистику не попадают. quarkslab/python-binexport: в `/contributors?anon=1`
   6 пользователей (100 коммитов), 2 бота (11) и 6 анонимных (58); в `/stats/contributors` 8 авторов и
   83 коммита, анонимных там нет вовсе (разница 111 и 83 - merge-коммиты). Боты с аккаунтом
   (dependabot и подобные), судя по этому примеру (8 авторов при 6 пользователях и 2 ботах), считаются
   авторами наравне с людьми; отдельно это не проверялось.
4. **204 - не обязательно пустой репозиторий.** Документация обещает 204 для пустого репозитория,
   но так же GitHub отвечает, когда все авторы анонимны. В пилоте 4 ответа 204 из 145, и все 4
   репозитория непустые: acheong08/DuckDuckGo-API (18 анонимных коммитов),
   cryptotorpo/Simple_Game_ERC721_Template, jenpet/plooral, stefanwille/openapi-generator-typescript-example,
   у всех `contributors_total = 1`. Поэтому после 204 строк у репозитория нет (недели неизвестны, а не
   нулевые; строки прошлого ответа удаляются), чекпоинт `empty`, а `contributors_total` запрашивается, как после 200. Отличить пустой
   репозиторий: `contributors_total = 0`.
5. **Обрезка списка авторов: 100 или около 500.** Документация графика Contributors говорит про
   топ-100, для REST оговорки нет. Проверка 19.11.2026 на pallets/flask: в ответе ровно 100 авторов
   (от 3 до 975 коммитов, сумма 2931), в ветке по умолчанию 5566 коммитов, контрибьюторов 864. Но
   потолок не у всех один. После полного сбора (20.11.2026) ответы перепроверены у 25 репозиториев
   с `contributors_total >= 100` без пометки и ещё у 74 средних. У 50 помеченных в ответе ровно 100
   авторов; из 25 непомеченных у 9 от 497 до 500 (NVIDIA/tensorflow 500,
   llvm/llvm-project-release-prs 499, langgenius/dify 498, AU-14/ColonialMarinesUniverse 497), у 7 между 100 и 500 (tchapgouv/tchap-ios 164 при 400
   контрибьюторах, kdrag0n/proton_kernel_wahoo 330, komikku-app/komikku 440). От чего зависит потолок,
   не выяснено. Признак обрезки (`stats_truncated = true`): ровно 100 авторов или 490 и больше. У
   репозитория, где авторов действительно 100, пометка ложная, таких единицы; ответ из 101-489 авторов
   считаем полным. Строки недель для обрезанных пишутся (они верны для авторов из ответа), но `commits`
   и `contributors` занижены: в расчёты такие репозитории идут с оговоркой или исключаются.
6. **`contributors_total` с анонимными** (`anon=1`): у flask 864 с ними и 399 без них. Это число
   людей (адресов), а не аккаунтов. `mentionableUsers` из GraphQL - другое множество (727 у flask).
   Число бывает меньше авторов из статистики: у komikku-app/komikku 312 при 440 авторах, у
   neo4j-labs/llm-graph-builder 22 при 28 авторах в одну неделю. Причина не выяснена; это оценка
   снизу, а не точный счёт.
7. **403 на гигантских репозиториях**: torvalds/linux на `/contributors` отвечает 403 "The history or
   contributor list is too large". Это не лимит запросов, `contributors_total = NULL`.
8. **История раньше `created_at`**: проект перенесли на GitHub вместе с историей. В пилоте у 10 из 141
   репозиториев с коммитами первые коммиты раньше недели создания, у 2 больше чем на год
   (planetscale/docs создан в 2021, коммиты с 2018-05; quarkslab/python-binexport создан в 2023,
   коммиты с 2018-10). Для когорт и признаков "активность после создания" отсекайте по `created_at`.
   В полном сборе таких 537 репозиториев из 5332 (у 157 больше чем на год): 44 284 недели и 865 297
   коммитов раньше недели создания, 42% всех коммитов в таблице, из них 765 876 у десяти
   репозиториев (llvm/llvm-project-release-prs 310 926, KudProject/kernel_xiaomi_sdm710 284 958). У 10
   ряд начинается раньше 2008 года, у двух в 1970-1972: это неверные даты коммитов, а не история.
   Неделя создания и всё после неё:
   `WHERE w.week > (r.created_at AT TIME ZONE 'UTC')::date - 7` (не `date_trunc('week', ...)`: та
   считает неделю с понедельника).
9. **Состояние на дату сбора.** Force-push в ветку по умолчанию переписывает и прошлые недели;
   повторный сбор заменяет снимок репозитория целиком (выше). Данные релиза `data-commits-2026-11-20`
   собраны до этого исправления, но каждый репозиторий там записан одним ответом полного сбора; поверх
   ответа пилота того же дня записаны только 145 репозиториев пилота.
10. **Статистика может не посчитаться.** После 4 раундов `202` репозиторий остаётся без строк и без
    чекпоинта (`pending_repos` в журнале), следующий запуск с `--resume` спросит его снова. У
    blawar/titledb (45 ГБ, 641 коммит) статистика не посчиталась ни в полном сборе, ни в повторе с
    `--resume` 20.11.2026 (ещё 4 раунда): видимо, GitHub не считает её для репозиториев такого объёма.

## Как идёт сбор

- `202 Accepted` - GitHub считает статистику в фоне. Это не ошибка: репозиторий уходит в очередь
  следующего раунда, всего раундов 4. Если раунд короче 30 секунд (маленький `--limit`), перед
  следующим ждём остаток; после последнего раунда не ждём. Сна на каждом 202 нет.
- `contributors_total` - один запрос на репозиторий после 200 или 204, а не на каждом раунде.
- Чекпоинты `core.checkpoints`, source `github-commits`, ключ - id репозитория, значение `done`,
  `empty` (204 или `[]`) или `missing` (404). Пишутся после строк. У отложенного (202) и у
  репозитория с ошибкой после всех повторов чекпоинта нет. `--resume` пропускает всё, у чего чекпоинт
  есть.
- Журнал `core.collection_runs`: `params` = `from`, `to`, `min_stars`, `limit`, `resume`; `stats` =
  `rest_requests`, `rounds`, `pending_repos` и `truncated_repos` (всегда, в том числе 0), а также
  `done_repos`, `empty_repos`, `missing_repos`, `failed_repos`, `resumed_repos`, `round_wait_s`,
  `retries`, `rate_limit_wait_s`, `http_4xx`, `http_5xx`, если они были.
- Лимит REST - 5000 запросов в час. Когда остаётся меньше 50, клиент спит до сброса окна и идёт
  дальше; 403 с `x-ratelimit-remaining: 0` тоже ждёт сброса, а не роняет сбор.

## Как воспроизвести

```bash
set -a && . ./.env && set +a
export SPRING_DATASOURCE_PASSWORD="$POSTGRES_PASSWORD" COLLECTOR_GITHUB_TOKENS="$(gh auth token)"
mvn -q -DskipTests package
# пилот
java -jar collector/app/target/collector.jar --source=github-commits \
     --from=2023-03-01 --to=2023-03-31 --min-stars=10 --limit=30
# полный сбор; после остановки тот же запуск с --resume продолжит с отложенных и упавших
java -jar collector/app/target/collector.jar --source=github-commits \
     --from=2018-01-01 --to=2025-12-31 --min-stars=10 --limit=0
```

```sql
SELECT count(DISTINCT repo_id) AS repos, count(*) AS rows, min(week), max(week) FROM core.repo_commits_weekly;
SELECT DISTINCT extract(isodow FROM week) FROM core.repo_commits_weekly;          -- только 7
SELECT value, count(*) FROM core.checkpoints WHERE source = 'github-commits' GROUP BY value;
SELECT count(*) FILTER (WHERE stats_truncated) AS truncated, count(contributors_total) AS with_total,
       count(stats_truncated) AS processed FROM core.repos;
SELECT params, stats FROM core.collection_runs WHERE source = 'github-commits' ORDER BY id DESC LIMIT 1;
```
