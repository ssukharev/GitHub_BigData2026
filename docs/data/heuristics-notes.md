# Выборка github-repos: как собрана, эвристики, смещения

Текст для раздела статьи "Данные". Код: `RepoCollector`, `SampleWindowPlanner`, `RepoFeatureDetector`
в `collector/github`.

## Как собрана выборка

- **Совокупность**: публичные репозитории (не форки) с `stars >= 10` на дату сбора, созданные
  2018-01-01..2025-12-31 по UTC. Строка поиска одна для подсчёта и для сбора:
  `is:public stars:>=10 created:A..B`.
- **Страты**: календарные месяцы создания, 96 штук. Население месяца - `repositoryCount` одного
  запроса на месяц, измеренный на старте запуска. Он записан в `docs/data/population-by-month.csv`
  и в чекпоинт `plan:...`, поэтому `--resume` считает веса по тем же числам.
- **Квота месяца**: `limit / 96` с накопленным округлением, сумма квот ровно `limit`
  (при `limit = 5000` каждая квота 52 или 53). Квоты равные, а не пропорциональные населению:
  для рядов по месяцам нужно сопоставимое число наблюдений в каждом месяце.
- **Окна**: каждый месяц нарезан на 10-минутные окна по UTC (4464 окна в 31-дневном месяце),
  окна стыкуются без дыр и пересечений (`[A, A + 10 мин - 1 с]`, обе границы входят). Окна
  месяца перемешаны генератором `SplittableRandom` с зерном из `seed` (по умолчанию 42) и месяца.
  Сборщик идёт по окнам в этом порядке и забирает каждое окно **целиком**, пока в месяце набрано
  меньше квоты. Взятые окна в порядке взятия - `docs/data/sample-windows.csv`.
- **Почему не "первые N результатов"**: для запроса из одних квалификаторов поиск GitHub отдаёт
  репозитории по убыванию звёзд. Замер 17.11.2026 (март 2023, `stars >= 10`): ответ без `sort`
  совпал с `sort:stars-desc`, у первого результата 188 072 звезды, у тысячного 446, среди первой
  тысячи нет ни одного нарушения порядка. "Первые N" - это N самых популярных, поэтому порядок
  GitHub выборку не определяет: окно берётся целиком, а случайность наша (по `seed`).
- **Кто в выборке**: репозиторий входит в выборку, если его `created_at` попадает в одно из окон
  `sample-windows.csv`. Так отсеиваются строки `core.repos` из пилотов и других слоёв. Месяц,
  взятый целиком (население не больше квоты или `--limit=0`), строк в этом файле не даёт;
  при `stars >= 10` и `limit = 5000` таких месяцев нет: население месяца 15-26 тысяч.

## Веса

Приближённый постстратификационный вес строки = население месяца / число репозиториев, взятых в этом месяце. На пилоте
(2019-03..2019-04, `limit = 100`, `seed = 42`): март 21 180 / 51 = 415,3; апрель 20 049 / 60 = 334,2.
Эти веса приводят суммарный вес каждого месяца к его населению и позволяют описывать данные
с поправкой на разные размеры месяцев. Это не обратные вероятности включения и не гарантия
несмещённой оценки всей совокупности: число взятых окон зависит от их размеров, поскольку сбор
останавливается после достижения квоты репозиториев. Доли без весов описывают саму выборку;
взвешенные доли — приближённое постстратифицированное описание с этим ограничением.

Контрпример правила остановки: в месяце два окна с 1 и 9 репозиториями, квота 5. При случайном
порядке большое окно берётся всегда, маленькое — только когда идёт первым (вероятности 1 и 1/2).
Если положительный признак есть лишь у одного репозитория маленького окна, истинная доля — 1/10.
Текущее правило и веса N/n дают долю 1/10 или 0 в двух равновероятных порядках, то есть в среднем
1/20. Поэтому веса не устраняют возможную связь размера окна с признаками репозиториев.
Для обобщения на всю совокупность нужна отдельная проверка устойчивости к правилу отбора и seed;
опубликованная выборка и её веса не объявляются дизайн-несмещёнными.

```python
pop = pd.read_csv("docs/data/population-by-month.csv", parse_dates=["month"]).set_index("month")["population"]
repos["month"] = repos["created_at"].dt.tz_localize(None).dt.to_period("M").dt.to_timestamp()
repos["weight"] = repos["month"].map(pop) / repos.groupby("month")["month"].transform("size")
share_ci = (repos["has_ci"] * repos["weight"]).sum() / repos["weight"].sum()   # строки с NULL отфильтровать заранее
```

## Признаки has_tests, has_ci, has_docker

Считаются по именам в корне (`HEAD:`), в `src` (`HEAD:src`) и в `.github` (`HEAD:.github`) ветки по
умолчанию. Регистр не важен; каталог (`tree`) и файл (`blob`) с одним именем - разные сигналы.

| Признак | Сигнал |
|---|---|
| `has_tests` | каталог в корне `test`, `tests`, `__tests__`, `spec`, `specs`; каталог в `src`: `test`, `tests`, `__tests__` (Maven и Gradle: `src/test`); файл в корне `test_*.py`, `*_test.py`, `*_test.go`, `*_spec.rb`, `*.test.js`, `*.spec.ts` и другие расширения JS/TS |
| `has_ci` | каталог `workflows` в `.github` (в git нет пустых каталогов, значит, внутри хотя бы один файл); в корне файл `.gitlab-ci.yml`, `.travis.yml`, `Jenkinsfile`, `azure-pipelines.yml`, `bitbucket-pipelines.yml` или каталог `.circleci` |
| `has_docker` | файл в корне `Dockerfile`, `Dockerfile.*`, `docker-compose.yml`/`.yaml`, `compose.yml`/`.yaml` |
| все три | `NULL`, если у репозитория нет корневого дерева (пустой репозиторий): признак неизвестен, а не "нет" |

Пилот (111 репозиториев, без весов): `has_tests` 0,22, `has_ci` 0,14, `has_docker` 0,02.

### Ограничения эвристик

- **Ложноотрицательные**: монорепозитории (`packages/*/tests`), многомодульные Maven и Gradle
  (`app/src/test`), тесты рядом с кодом глубже корня (пакеты Go в подкаталогах, Rust с тестами
  внутри исходников), CI, настроенный во внешнем сервисе без файла в репозитории, `Dockerfile`
  в `docker/` или `deploy/`, `*.dockerfile` и `Containerfile`.
- **Ложноположительные**: каталог `tests` с одним `.gitkeep` из шаблона, workflow, который только
  ставит метки или закрывает старые issues, `Dockerfile` из генератора проекта, скрипты
  `test_*.py` в корне, которые не являются тестами.
- Признаки описывают HEAD ветки по умолчанию на дату сбора, а не момент создания.
- Точность измерена сравнением с полным деревом файлов на 50 репозиториях выборки (ниже). Имена
  корня, `src` и `.github` лежат в `core.repo_tree_entries`, так что промахи разбираются запросом без
  новых обращений к GitHub.

### Проверка по полному дереву файлов (23.11.2026, #57)

**Метод.** Эвристика смотрит только на имена в корне, `src` и `.github`. Эталон для тех же
репозиториев строится скриптом `analytics-py/quality/heuristics_check.py` по всему дереву ветки по
умолчанию (REST `git/trees/<ветка>?recursive=1`) и по содержимому workflow GitHub Actions. Это не
ручной просмотр репозиториев: эталон тоже читает имена, но на любой глубине и с проверкой
содержимого. Правила эталона (вложенные `node_modules/`, `vendor/` и подобные пропускаются):

- тесты: каталог `test`, `tests`, `__tests__`, `spec`, `specs`, `e2e`, `androidTest`, `unittest(s)` на
  любой глубине, в котором есть хотя бы один файл с кодом, или непустой файл с именем теста
  (`test_*.py`, `*_test.go`, `*.test.ts`, `*Test.java` и другие) вне `docs/` и `examples/`; каталог
  только с `.gitkeep` или README тестами не считается;
- CI: workflow с шагом `run:` или с action, который не относится к обслуживанию репозитория
  (checkout, stale, labeler, приветствия, черновики релизов); вызов чужого переиспользуемого
  workflow - только если в его имени есть build, test, lint или check; или непустой конфиг другого
  CI-сервиса на любой глубине;
- Docker: непустой `Dockerfile`, `Dockerfile.*`, `*.dockerfile`, `Containerfile` или compose-файл на
  любой глубине.

**Выборка.** 50 непустых репозиториев, стратифицированных по ответу эвристики, чтобы у каждого
признака были положительные случаи (`has_docker` истинен только у 6% выборки): `docker` 10 из 323,
`ci` (без docker) 12 из 1271, `tests` (без ci и docker) 10 из 354, ни одного признака 18 из 3281.
Внутри страты порядок задаёт `md5('57:' || id)`, выбор воспроизводит
`sql/quality/heuristics_sample.sql`. Взвешенные оценки - с весом "размер страты / взято из страты".
Эталон снят 23.11.2026, эвристика - на дату сбора 18.11.2026; автор не обнаружил изменений за
эти дни среди расхождений. Это сравнение снимков разных дат, а не независимая ручная разметка.
Все 50 деревьев были получены без признака усечения. При исходном прогоне скрипт проверял до 8
workflow на репозиторий в порядке имени файла; число остальных workflow не сохранялось. Поэтому
зафиксированные метрики CI относятся именно к этому ограниченному эталону. При новых прогонах
проверяются все workflow; неполное дерево или ошибка чтения не заменяются отрицательной меткой,
а прерывают публикацию новых результатов, не перезаписывая CSV прошлой успешной проверки.

Все расхождения (`docs/data/heuristics-check-2026-11.csv`, с путями-доказательствами):

- `has_tests` пропущены (5): тесты в каталоге пакета (DTUWindEnergy/TopFarm2: `topfarm/tests/`),
  тестовый проект .NET внутри `src` (tlbx-ai/tlbx: `src/*.Tests/`), монорепозиторий
  (deriv-com/dtrader-template: `packages/api-v2/src/__tests__/`), модуль Android
  (UxHarshit/ProCodeLC: `ProCodeApp/app/src/test/`, это шаблонные тесты Android Studio) и
  suanfaxiaohuo/SwinOCSR, где найденный тест принадлежит вложенной копии библиотеки pycocoevalcap
  (`model/pycocoevalcap/meteor/test_meteor.py`): эталон по именам считает её тестами проекта, хотя
  своих тестов у проекта нет.
- `has_ci` ложно истинен (1): Mods-Center/HyperOS-App-Vault - единственный workflow вызывает чужой

- `has_docker` пропущен (1): forderud/QtWasm - `image/Dockerfile` ниже корня.

**Что это значит.** В этой проверке найденный признак почти всегда совпадает с эталоном
(взвешенная точность 0,92-1,00). Для `has_tests` и `has_docker` наблюдались только пропуски:
эвристика теряет проекты, где тесты или Dockerfile лежат глубже корня и `src`. Это свидетельство
возможного занижения долей, но не доказательство нижней границы по всей совокупности: эталон
сам основан на правилах, а 50 проверок недостаточно, чтобы исключить ложноположительные ответы.
Для `has_ci` наблюдалось высокое согласие с ограниченным эталоном.
Взвешенная полнота держится на страте без признаков (18 репозиториев с весом 182 каждый): два
пропуска тестов и один пропуск Docker в ней дают полноту 0,58 и 0,64, и эта оценка грубая. Без
спорного SwinOCSR взвешенная полнота `has_tests` была бы 0,66.

### README

README берётся по REST (`GET /repos/{owner}/{repo}/readme`): это "preferred README", который GitHub
показывает на странице репозитория (корень, `.github/` или `docs/`, любой регистр и расширение).
Строка с `text = NULL` значит "проверили, README нет"; отсутствие строки значит "не проверяли или
запрос упал". Упавшие запросы повторяются в конце запуска для всех репозиториев периода без строки
в `core.readmes`.

## Что остаётся смещённым

- **Порог звёзд измеряется на дату сбора**, а не на дату создания: репозитории последних лет не
  успели набрать 10 звёзд. Ряд населения (замер 18.11.2026, всего 1 804 176): 17-26 тысяч в месяц
  в 2018-2021 и в основном 15-18 тысяч в 2024-2025.
- **Возраст**: у старых репозиториев было больше времени добавить CI, тесты и Docker; сравнивать
  `has_*` между годами нужно с этой оговоркой.
- **`has_*` и README** - состояние HEAD на дату сбора.
- **Кластерность**: репозитории одного окна коррелируют (один автор, одно мероприятие), поэтому
  эффективный размер выборки меньше числа строк. В полной выборке 1229 окон, в окне в среднем
  4,3 репозитория, максимум 21.
- **Накрутка звёзд**: в 2025 году встречаются сети пустых репозиториев с одинаковым числом звёзд
  (например, 25.02.2025: 15 репозиториев у 5 аккаунтов, у всех ровно 17 звёзд, нет описания и
  языка, имена из 2-3 символов). В выборке таких около 28 (0,5%), почти все в 2025 году. Для
  задачи 5 это `unclear`; для остальных задач их стоит исключать фильтром или оговорить.
- **Правило остановки**: окно берётся целиком, поэтому в месяце оказывается от квоты до квоты плюс
  размер последнего окна. При `limit = 5000` квота месяца 52, взято от 52 до 72 (в среднем 54,7),
  всего 5250. Вес считается по фактическому числу взятых, но не исправляет неравные вероятности
  включения окон разного размера (см. раздел «Веса»).
- **Предел поиска**: если любая страница окна сообщает больше 1000 репозиториев, сбор прекращается
  до записи этой страницы и не отмечает окно завершённым. Первые 1000 популярных результатов
  нельзя выдавать за полное случайно выбранное окно; такой интервал надо предварительно раздробить.
- **Форки и приватные репозитории** исключены самим запросом.
- **Живой индекс поиска**: между запусками `repositoryCount` месяца и содержимое окна меняются на
  единицы (звёзды пересекают порог, репозитории удаляют). Население фиксируется в чекпоинте плана,
  а `population-by-month.csv` перезаписывается числами, измеренными на старте запуска.

## Как воспроизвести

```bash
java -jar collector/app/target/collector.jar --source=github-repos \
     --from=2018-01-01 --to=2025-12-31 --min-stars=10 --limit=5000 --seed=42
```

Тот же `seed` даёт тот же порядок окон. После обрыва - те же параметры и `--resume`: окна с
`done:` в `core.checkpoints` берутся без запросов. Одна база - одна выборка: запуск с другим
`--seed`, `--limit` или `--min-stars` на тех же таблицах смешает выборки и испортит веса.
